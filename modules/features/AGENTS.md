# features — opt-in feature modules

## Purpose
One directory per app/concern. Import is enabling: hosts/bundles add `self.nixosModules.<name>` or `self.homeManagerModules.<name>` to their `imports`. Each `default.nix` is a flake-parts module exporting those lower-level modules.

## Ownership
Each `features/<name>/default.nix` owns its feature. Shared patterns: out-of-store symlinks, `_*.pkg.nix` derivations, pinned flake inputs.

## Local Contracts
- **Import = enable.** No feature-defines-flag pattern. Feature is active when its module is in `imports`.
- **Module flavor by scope:**
  - System-wide (daemon, `environment.systemPackages`, NixOS option): `flake.nixosModules.<name>`.
  - Per-user (dotfiles, HM programs): `flake.homeManagerModules.<name>`.
  - Some features export both.
- **Out-of-store symlinks for live-editable config:** `fish`, `ghostty`, `niri`, `nvf`, `omp`, `opencode` link their config trees back into this checkout (e.g. `~/.config/fish` → repo path) via `mkOutOfStoreSymlink`. Edits in the repo are live without rebuild. Because the agent trees (`features/omp/home`, `features/pi-coding-agent/home/agent`) are linked the same way, each carries its own nested `.gitignore` as the single list of runtime paths (sessions, caches, dbs, downloaded toolchains, browser profiles) that must never be committed.
- **User-scoped services carry an explicit PATH.** `systemd.user.services.<name>` starts with systemd's compiled-in search path, which excludes `/run/current-system/sw/bin`. List every binary the service runs in `Service.Environment.PATH` (`lib.makeBinPath`); `herdr` needs `git`, `curl`, and `coreutils`, `herdr-web` needs `herdr`, `zoxide`, `find`, and `ss`, while `wayfinder-dashboard` needs `gh`, `herdr`, and Pi.
- **A loopback service reaches the tailnet through an opt-in option.** `herdr-web`, `herdr-web-ui`, and `wayfinder-dashboard` each declare `services.<name>.tailscaleServe` on their NixOS module and read the port and bind address back from the home-manager service, so a change cannot make the proxy and the listener disagree. The unit is a oneshot: `tailscale serve --bg` writes the mapping, and `ExecStop` removes that port with `tailscale serve --https=<port> off`. They use separate loopback/tailnet port pairs (7930/17930, 7317/17317, 8787/18787) and are published independently.
- **A host-scoped feature carries its own home-manager half.** The three tailnet bridges are NIXPC-only, so their NixOS module adds the matching `homeManagerModules.<name>` to `home-manager.sharedModules` instead of the module being listed in `system/home-manager`'s all-host set. Importing the NixOS module is then the whole enable switch, and the other host never reaches the service, its package, or its derivation closure. The assertions stay gated with `lib.optionals cfg.tailscaleServe.enable [ … ]` so importing the module alone does not demand `services.tailscale`. `herdr` uses the same shape for a different reason: its daemon is a user service with no NixOS half at all, so the exported NixOS module exists only to inject the home-manager half, and the host that imports it is the host that wants a managed daemon.
- **A bun dependency tree is a fixed-output derivation, and its hash is per-architecture.** `herdr-web-ui` cannot use `buildNpmPackage`: `bun.lock`'s `patchedDependencies` carries the xterm IME backport that Vite builds from xterm *source*, which a `package-lock.json` cannot express, and bun2nix 2.1.2 rejects bun 1.4's lockfile v2 (accepted only by an unmerged PR). So `_herdr-web-ui.pkg.nix` runs `bun install --frozen-lockfile` once in a `outputHashMode = "recursive"` FOD and hands the tree to a normal derivation. Two consequences a reader of that file must know: an FOD may not reference store paths, so the FOD skips `fixupPhase` and the consumer copies `node_modules` out and runs `patchShebangs` itself; and `node` is a runtime dependency of the app (the terminal-attach sidecar), not just `bun`. The recursive hash also covers the platform packages bun resolves (esbuild, oxide, `@lydell/node-pty`), so the pinned value only holds on the architecture it was taken on — x86_64-linux. On aarch64 the tree differs and the build fails with a hash mismatch, which is why the feature is NIXPC-only rather than a hash problem to chase.
- **`mango`'s config keywords belong to upstream and break builds, not runtime.** The feature validates at build time (`mango -c <file> -p`), and the new mango rejects a config on the *first* unknown keyword, on any config value over 255 bytes, and on any key-binding conflict — each aborts the whole rebuild, not just the feature. Upstream renamed most keywords to snake_case at mangowm `0fbfef4b` (`monitorrule`→`monitor_rule`, `gappih`→`gap_inner_horizontal`, `exec-once`→`exec_once`, `appid`→`app_id`, `isfloating`→`is_floating`, …). The mapping is documented in `features/mango/default.nix`'s header. After any `mangowm` bump, read the authoritative keyword list out of the new input's `src/config/option_defs.c` — `grep -oP '(?<=strcmp\(key, ")[a-z0-9_-]+'` — before touching anything else, and keep any long command in a `pkgs.writeShellScript` (the `swaylock` bind is exactly this case: 305 bytes inline, now a `mango-swaylock` helper) rather than inlining it.
- **A host that must never build remotely pins the *setting*, not just the list.** `nix.buildMachines = []` means "write no `/etc/nix/machines`" (`nix-remote-build.nix`), not "write an empty one", so a file left by an older generation still applies through the default `builders = @/etc/nix/machines`. ASAHI therefore also forces `nix.settings."build-machines" = ""`. Until that generation is live, an existing machines file keeps routing work off-box, so a one-off build still needs `--builders ''`.
- **A feature on both hosts takes its machine facts as options.** Import stays the enable switch; what differs per machine arrives through a `dendritic.<feature>` option set that the host assigns from its `hosts/<HOST>/_<feature>-settings.nix`. `mango` (issue #245) declares `dendritic.mango.{monitorRule,extraEnv,extraBinds,gaps,borderWidth,xkbRulesLayout}` (an undeclared key in a host's `_<feature>-settings.nix` is a hard eval error, not a warning; the input's trackpad keys are therefore compositor-side only — see the `tap_to_click` comment in `features/mango/default.nix`); a module that declares `options` MUST put its configuration under an explicit `config` attribute (`imports` stays a module key at the top level).
- **`_` data files:** `_<name>.pkg.nix` derivations, language lists, generated configs — skipped by `import-tree`, imported explicitly by `default.nix`.
- **A feature publishes a reusable value at its part's top level, as data.** `self.scheme` and `self.fonts.marathon` are the two examples. The output must be declared in `parts.nix` (`options.flake.<name>`), it cannot be set from inside `perSystem` — perSystem's option set holds only flake-parts' predeclared outputs, so a custom attr there fails with ``option `perSystem.<sys>.fonts' does not exist`` even when declared — and per-system content is published as **names, not derivations** (`map (name: pkgs.${name}) self.fonts.marathon`) so the value never captures one system's pkgs.
- **Docker Compose stacks pair a `compose.yaml` with its `compose2nix` output.** The compose file is the source of truth, the generated module sits beside it behind the `_` prefix, and the feature's `default.nix` adds what compose2nix cannot express (child image, secret files, mount ordering, tailnet publish). `paseo` is the reference example.
- **`wayfinder-dashboard` runs in the user's trust context.** Its Deno service needs the authenticated `gh`, the live Herdr socket, and Pi, so its NixOS import pulls in a Home Manager user service rather than a container. Projects are durable coordinates (`repo`, checkout, Herdr workspace); GitHub remains canonical. A launch refetches the map frontier, claims the ticket, creates one tab in the project's workspace, starts Pi, and submits a one-ticket Wayfinder brief. Each launch records the ticket's `paneId`, and that record gates every read and keystroke route, so the app can drive its own tickets' panes and nothing else.
- **Pinned inputs as source trees:** `dojjo` (v0.2.2, `flake=false`) is consumed via its `_*pkg.nix` package derivation. `retrosmart-cursor` (tag v2.0.1, `flake=false`) is the same: its XPM artwork and build scripts feed `features/retrosmart-cursor/_retrosmart-cursor.pkg.nix`.
- **Human-readable output is HTML, in the Marathon theme.** The feature's `home/agent/AGENTS.md` is the global agent contract, and it routes every spec, plan, exploration, review, and report to a self-contained artifact in `<repo>/artifacts/`. The `html-artifacts` skill (global `~/.agents/skills`, symlinked into `home/agent/skills/`) carries the template and the style contract; the theme's colors live in the template's `:root`, not in `scheme`, because these pages are read in a browser outside the pi TUI.
- **`programming` owns the Marathon type stack, published as `flake.fonts.marathon`.** The four free (OFL) stand-ins for Bungie's commercial Marathon faces: `oswald` (game main), `jetbrains-mono` (secondary), `orbitron` (tertiary), `source-serif` (quaternary). IvyPresto Display — the one real Marathon face that is actually free — is not in nixpkgs; vendoring it is the only reason to revisit. `jetbrains` in nixpkgs is the IDE scope, not the font. The attr holds **names, not derivations** and is consumed as `map (name: pkgs.${name}) self.fonts.marathon`. They land in that module's `home.packages` plus `fonts.fontconfig.enable = true`, because Home Manager has no `fonts.packages` option and fontconfig discovers fonts through `home.packages` (`system/home-manager` sets `useUserPackages = true`). Any feature can now name the same families — the html-artifacts theme already names Oswald and JetBrains Mono and resolves them locally instead of over the network.
- **`easyeffects` follows the upstream NixOS recipe, not a system package.** The [wiki](https://github.com/wwmm/easyeffects/wiki/Package-Repositories#nixos) asks for exactly two things, on opposite sides: HM `services.easyeffects.enable = true;` and NixOS `programs.dconf.enable = true;`. A bare `easyeffects` entry in `environment.systemPackages` installs the binary and nothing else — no preset wiring, no dconf writer, no `~/.config/easyeffects`. So the feature exports both halves; its NixOS module enables dconf and injects the HM half through `home-manager.sharedModules` (the `wayfinder-dashboard` pattern), which makes `system/audio`'s single import the whole enable switch on both hosts.
- **`herdr` owns the daemon; every herdr client is ordered after it.** `herdr.service` (`features/herdr`) runs `herdr server` with the PATH the daemon needs — `git` above all, because herdr's worktree runtime shells out for every worktree operation and has no in-process git, so a daemon without git fails `worktree list/open/create` with `No such file or directory (os error 2)`. `herdr-web`, `herdr-web-ui`, and `wayfinder-dashboard` carry `Wants`/`After = [ "herdr.service" ]` and nothing else may start the daemon: `herdr-web`'s `ensureServer` is a ping-then-spawn, and its detached fallback spawn inherits *that* unit's PATH, which is how the daemon ended up git-less and pi-cowboy could not create a single worktree. The unit holds its start job open with an `ExecStartPost` readiness probe (`herdr agent list` — exit 1 with no server, 0 with one, where `herdr status` exits 0 either way), so `After=` really does guarantee a live socket. Three lifecycle details shape the policy: a second `herdr server` exits 1 while another owns the socket, so `Restart=on-failure` is capped by `StartLimitBurst`/`StartLimitIntervalSec` rather than left to spin; a deliberate `herdr server stop` exits 0, so `on-failure` does not resurrect it; and a SIGKILLed server leaves a stale socket that the daemon unlinks and rebinds itself, so the restart path needs no cleanup. **One-time cutover:** a daemon already running detached (started by an older `herdr-web`) is not systemd-owned, so `herdr server stop` it once by hand — a competing unit start otherwise just fails with "herdr server is already running".
- **`vesktop` declares settings it cannot own, and says so.** `programs.vesktop` installs no package of its own (its shared `mkVesktopLikeModule` runs with `installPackage = false`; the vesktop module adds the overridden package itself), so `enable = true` is the install switch and `package` is not. Vesktop and Vencord both rewrite their settings files at runtime, so both trees set `mutableSettings = true` — declared values merge into a real user-owned file at activation (declared wins, arrays replaced, close the app first). The sepia Discord theme is delivered as a theme **file** (`vencord.themes.sepia` + `enabledThemes`), never as `vencord.extraQuickCss`: quickCss.css is written back by Vencord's in-app editor, so a store symlink there would break that editor on every save, while theme files are read-only to Vencord. Both the theme's CSS variables and the splash colors read `self.scheme`; Discord's variable names churn between releases, so the map carries only the long-lived ones and a stale name degrades to Discord's own color.
- **`pi-bolt` is the same Pi on a second runtime, not a second config.** It reads the same `~/.pi/agent` tree (settings, extensions, skills, the `sepia` theme), so nothing is duplicated in its feature; only the binary is added to PATH as `pi-bolt`, never `pi`. Two contracts hold it together: its ELF is a Bun standalone binary that must get PT_INTERP and NO rpath (any rpath makes it segfault on startup; the launcher sets `LD_LIBRARY_PATH` instead), and the pinned release embeds its own Pi build, which is not necessarily `pkgs.pi-coding-agent`'s version — re-check `pi-bolt list` after a bump. See `features/pi-bolt/AGENTS.md`. It is imported by the **NIXPC host**, not by a bundle, because ASAHI runs no coding agents.
- **Feature table (current):** `act`, `agent-browser`, `brave`, `clipboard`, `computer-use`, `docker` (+ `mcp-containers.nix`), `dojjo`, `easyeffects`, `fish`, `flatpak`, `funes`, `gaming-tools`, `ghostty`, `herdr` (NIXPC only), `herdr-web` (NIXPC only), `herdr-web-ui` (NIXPC only), `lazygit`, `leetcode`, `mango`, `nautilus`, `niri`, `nixpc-desktop`, `noctalia`, `noctalia-greeter`, `nushell`, `nvf`, `omp`, `opencode`, `paseo` (NIXPC only), `pi-bolt` (NIXPC only), `posy-cursors`, `prismlauncher`, `programming`, `retrosmart-cursor`, `scheme`, `steam`, `stylix`, `usb-automount`, `vesktop`, `wayfinder-dashboard` (NIXPC only), `wayland-base`, `widevine`.
- **`flatpak` owns declarative Flatpak state through `nix-flatpak`.** `flatpakCommon` enables the service and weekly updates and owns **no application list**; `flatpakNixpc` carries all four apps (OBS Studio, Sober, plus the pinned Spotifast and Nuvio release bundles) behind `lib.optionals pkgs.stdenv.hostPlatform.isx86_64`, and `flatpakAsahi` contributes none. `flatpakNixpc` splits them in two shapes: `nixpcAppIds` are bare Flathub ids, while its local `bundles` list holds `{ appId, sha256, bundle }` records for apps upstream ships only as a `.flatpak` release asset with no Flathub listing (Nuvio has none — `flathub.org/apps/com.nuvio.media.desktop` is 404). A bundle record replaces the plain appId, so the same id must never also be a bare id. `flatpakPackages.nixpc` stays the bare-id list (the published option is `listOf str`, so bundles cannot live there) and is consumed nowhere today. `common` is `[ ]` on purpose: a Flatpak the remote does not carry for the host arch makes `flatpak-managed-install.service` exit 1 on every activation, and `switch-to-configuration` then aborts with status 4. `com.obsproject.Studio` is Flathub **x86_64-only** (`arches: ["x86_64"]`, runtime `org.freedesktop.Platform/x86_64/*`) — never put it in a shared list. A `bundle` record replaces its bare appId string, so the same id must not appear twice. A bundle's runtime comes from its own release metadata rather than the remote's arch matrix, so a pinned bundle cannot fail the way a missing remote app does — but the runtime it names (`org.gnome.Platform//50` for Nuvio) still has to be installable from flathub. Both host modules inherit the common aspect, and hosts import exactly their own aspect.
- **`funes` ships the binary and stops there.** Its `funes add <agent>` step is interactive and writes into pi's git-tracked `~/.pi/agent` config (which is an out-of-store symlink into this repo), so no activation may run it; the user runs `funes add pi` once in a terminal. It is the one place where "install the tool" and "wire the tool into an agent" genuinely cannot both be declarative — see `features/funes/AGENTS.md`.
- **`funes` also owns the two commands it cannot work without:** `hf` (`python3Packages.huggingface-hub`), the only supported way to write the Hub token where funes reads it, and `trufflehog`, the mandatory secret scanner `funes push` hard-refuses to proceed without. Both are `environment.systemPackages`, same rationale as the binary itself — an agent driving `funes push` must find them. The scanner also needs one extra piece: `$FUNES_TRUFFLEHOG` points at the feature's `trufflehog-funes` shim instead of `pkgs.trufflehog`, because funes passes `--no-update` and nixpkgs' wrapper injects its own — a repeated flag that trufflehog rejects, which kills every scan-gated operation including `funes index`.
- **The keyboard layout has three channels and all three must agree per host:** `services.xserver.xkb.layout` (+ `variant`), `console.keyMap`, and `dendritic.mango.xkbRulesLayout` (rendered as mango's `xkb_rules_layout`). The compositor's own keymap is what actually types, so the mango one is the one that matters; the shared `system/core/locale.nix` defaults (`gb` / `uk`, both `mkDefault`) are the NIXPC values. ASAHI is `gb` variant `mac` ("English (UK, Macintosh)") → `gb(mac)`: Shift+3 = £, € and # on the third level of 2 and 3, Shift+2 = @ preserved, and the physical fn key reaches that third level because `systemd.services.evremap` in `asahiConfiguration.nix` remaps `KEY_FN` → `KEY_RIGHTALT`. macOS UK muscle memory, not the US keycaps — see `modules/hosts/AGENTS.md`.
- **The pointer cursor has two delivery channels.** `home.pointerCursor` (set by `features/retrosmart-cursor`) covers the home profile, `~/.icons`, the GTK cursor theme, and login shells. A greeter-spawned compositor takes its environment from its own config instead, so `mango`'s `settings.env` and niri's `config.kdl` `environment` block both carry `XCURSOR_THEME`, read from `self.retrosmartCursor`.
- **`scheme` owns every color.** It exports `flake.scheme` (roles, base16, ANSI, `museum` roles, noctalia/greeter/omp/html documents, wallpaper). A themed feature MUST read `self.scheme` instead of a local hex. Features that cannot read nix values keep a copy and name the file to sync. `scheme.museum` (`brassLt`/`paper3`/`patina`) is the museum reskin's escape hatch: those three materials have no M3 role to map onto, so they are the only museum tokens that are a value rather than a mapping. They are also merged into the rendered noctalia palette document as `dark.museum`, so the museum plugin resolves *every* token from `~/.config/noctalia/palettes/<name>.json` and carries no hex of its own — Noctalia reads the `m*` keys it knows and ignores the rest. `scheme.pi` is the pi TUI token map: all 53 required colors plus `thinkingMax`, `searchMatchBg` and `searchMatchText`, because pi silently falls back to its built-in `dark` theme for a missing token. `features/pi-coding-agent` writes it to `~/.pi/agent/themes/sepia.json` from `home.activation.piTheme`, which lives in the feature's **NixOS** module because `flake.homeManagerModules.pi-coding-agent` is exported but imported nowhere, and the module reaches this user's HM config through `home-manager.users.<name>`. A NixOS module's `lib` has no `hm`, so the dag comes from `inputs.home-manager.lib.hm.dag`. The file is selected by `"theme": "sepia"` in `pi-coding-agent/home/agent/settings.json`, and `agent/themes/` is gitignored because activation regenerates it.
- **nil is the Nix LSP, not nixd.** `features/nvf/default.nix` enables `vim.lsp.presets.nil` and configures `vim.lsp.servers.nil` inline (`root_markers`, `settings.nil.formatting.command` = store `nixfmt`); `features/nvf/_languages.nix` binds the server to the `nix` filetype. nvf ships a `nil.nix` preset, so there is no `_nixd.nix` data file any more. nil evaluates the workspace flake itself, so it needs none of nixd's hand-built `options.expr` provider table, and `system/home-manager` no longer exports `dendritic.nixdOptionTree`. Consequence: NixOS/Home Manager option completion now costs one flake eval instead of three provider evals, and nixd can no longer OOM this box (see the omp skill `git-push-large-file-history-rewrite`). nil's whole config surface is `settings.nil.*` (`docs/configuration.md`): `formatting.command`, `diagnostics.ignored`/`excludedFiles`, `nix.binary`/`maxMemoryMB`, `nix.flake.autoArchive`/`autoEvalInputs`/`nixpkgsInputName`.
- **nvf's `jls` package is not buildable on this flake, and it is off on purpose.** `nvf` follows our `nixpkgs`, and nvf's `flake/pkgs/by-name/jls` pins a `mvnHash` for a maven-deps FOD that this nixpkgs' `maven` (3.10.0) and `openjdk-headless-25` no longer resolve — the build dies with `hash mismatch in fixed-output derivation '…-maven-deps-jls-0.9.0.drv'`, which aborts the whole `nixos-rebuild` because nvf routes the package through `home-manager-generation`. Upstream main still carries the stale value, so bumping the input does not help. `jls` is reachable only through the **java DAP preset** (`vim.debugger.nvim-dap.adapters.jls`); java editing is `jdt-language-server` from nixpkgs and is unaffected. `features/nvf/_languages.nix` therefore sets `java.dap.enable = false`. To get the debugger back, either wait for nvf to ship a matching `mvnHash`, or vendor a jls derivation with `sha256-2HEZClbtiFAWuR8aIgaW1nMl05aI/tShnQFBptamfKQ=` (verified reproducible on ASAHI: rebuilding the FOD under that hash succeeded, and both trees NAR-hash identically) and `lib.mkForce` the adapter's `command` — nvf builds `packages.<system>.jls` from its own `inputs`, so no `pkgs` overlay can reach it.
- **`stylix` themes GTK and Qt from `self.scheme.base16`.** It exports both a `nixosModules` and a `homeManagerModules` output, because dconf and the system Qt platform theme are NixOS-side while the GTK CSS and Kvantum theme are HM-side. `autoEnable = false` and `homeManagerIntegration.autoImport = false` keep it off every application this flake themes itself; each new target is added explicitly.

## Work Guidance
- New feature: create `features/<name>/default.nix` as a flake-parts module; export the appropriate `flake.{nixos,homeManager}Modules.<name>`. Add row to `README.md` Features table.
- Prefer HM module for user config, NixOS module only when system integration is required.
- If the feature needs a derivation from a pinned input, add `_<name>.pkg.nix` beside `default.nix` and keep the input rev pinned in `flake.nix`.
- Live-editable configs: use out-of-store symlink + document it in the module header.

## Verification
- `nix-instantiate --parse modules/features/<name>/default.nix`
- `nix eval .#nixosConfigurations.NIXPC.config.home-manager.users.<user>.programs.<name> --impure` (HM features, via host eval)
- `nix flake check --impure` covers all features through host `imports`.
