Change record / herdr / 2026-10-15

herdr owns its own
daemon in features/herdr

The herdr server used to be a by-product: whichever client attached first started it, and herdr-web.service was that client — so the daemon inherited a five-directory PATH with no git, and every git worktree operation died with ENOENT. It is now a unit of its own, herdr.service, with a declared PATH and a readiness gate, and the three clients are ordered after it so none of them can take the spawn fallback again.

Prompt that produced thisI dont want the herdr server started by herdr web. It should be started by itself within features/herdr.
APPLIED

The daemon is a first-class unit, and the ordering is what makes it stick. herdr-web, herdr-web-ui and wayfinder-dashboard now carry Wants/After = [ "herdr.service" ], and the unit holds its start job open until the API socket answers — so ensureServer's ping cannot fail and its detached fallback spawn never fires. Files are written and the config evaluates; activating it needs a rebuild plus one restart, which ends every live pane, so that step is yours.

The unit / as written
# modules/features/herdr/default.nix (excerpt)
config.systemd.user.services.herdr = {
  Unit = {
    Description = "herdr: persistent terminal-workspace server";
    # A competing server exits 1 while another owns the socket, so
    # Restart=on-failure alone would spin. Three tries, then stop.
    StartLimitIntervalSec = 60;
    StartLimitBurst = 3;
  };

  Service = {
    Type = "simple";
    # Default socket: ~/.config/herdr/herdr.sock. Nothing here sets
    # HERDR_SOCKET_PATH, so every client finds the same server.
    ExecStart = "${herdr} server";
    ExecStartPost = "${waitReady}";
    Environment = [
      "PATH=${lib.makeBinPath (with pkgs; [ git curl coreutils ])}"
    ];
    Restart = "on-failure";    # a deliberate `server stop` exits 0
    RestartSec = 5;
  };

  Install.WantedBy = [ "default.target" ];
};

Cutover 03 Order matters
# 1. the currently-running daemon was spawned detached by the OLD herdr-web:
#    systemd does not own it, so the new unit would just fail with
#    "herdr server is already running". Stop it once, by hand.
herdr server stop                # ⚠ exits every pane process in this workspace

# 2. rebuild and switch
nixos-rebuild switch --flake ~/.config/dendritic#NIXPC

# 3. the unit starts with the session; confirm it owns the socket now
systemctl --user status herdr.service
herdr worktree list --cwd ~/.config/dendritic   # → real JSON, no ENOENT

# 4. and the thing this was all for
#    ask pi for a cowboy agent; the worktree is created instead of dying.
▸ Why step 1 cannot be automated away
There is no non-destructive way to hand a live socket to a new owner: the daemon that holds it is not a systemd unit, so nothing can stop it on the unit's behalf, and ExecStartPre = herdr server stop would kill the user's panes on every restart of the unit as well. Stopping it once by hand is the honest cost, and from then on the unit is the only owner — which is the property the old arrangement lacked.

Open decisions 03
▸ D1 — does ASAHI want the daemon too?
It is exported and host-agnostic; NIXPC is the only host importing it. The NIXPC-only rule in hosts/AGENTS.md exists because the bridges hand terminal control to whoever reaches them over the network — a user-manager Unix socket does not, so the daemon is arguably safe on ASAHI and would give it the same guaranteed-git environment. One import line either way. your call
▸ D2 — add pi to the daemon PATH?
Herdr resolves integration version probes through this PATH (noninteractive_process::command(requirement.binary)), so an agent binary that should report a version has to be listed here. Nothing depends on it today and the old minimal PATH had the same gap, so it is left out rather than coupling this unit to the pi feature — but it is the one addition a future version-probe failure will point at. follow-up
▸ D3 — herdr update vs the nix build
The unit runs pkgs.herdr — the nix build with the lld link fix from attrs/desktop — so the daemon's update path is nixos-rebuild, not herdr update. That was already true of the installed binary; owning the daemon just makes it explicit, and it is why the bridges never baked herdr into a wrapper. no action
