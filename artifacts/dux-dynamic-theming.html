Change / Dux shell / 2026-11-16

Dux suite in one folder,
matugen owns the colours

Two changes, one contract. The four Dux features (shell, greeter, search, calendar) collapse into modules/features/dux/ with the shell's whole programs.dank-material-shell block in one shared attrset, so NixPC and ASAHI cannot drift. And the colour source for GTK, Qt, MangoWM and the terminal moves from the build-time sepia palette to the shell's wallpaper-derived matugen palette — a wallpaper change recolours the session without a rebuild.

Prompt that produced thisenable theming with dms programs.dms-shell = { enable = true; systemd = { enable = true; restartIfChanged = true; }; enableSystemMonitoring = true; enableVPN = true; enableDynamicTheming = true; enableAudioWavelength = true; enableCalendarEvents = true; }; otherwise known as dux shell, and ensure all the configs are synced within the dux folder. It should be the same on both nixpc and asahi.

↳ follow-ups: "One dux folder, all shell config" · "use dynamic mutagen with sylix so it syncs the color change all over the system" · "Full handover (all consumers)"

◈ TRADEOFF // upstream's defaults, written down
// shared by BOTH halves and BOTH hosts
let shared = {
  enable = true;
  enableSystemMonitoring = true;
  enableVPN = true;
  enableDynamicTheming = true;  # matugen
  enableAudioWavelength = true;  # cava
  enableCalendarEvents = true;   # khal
}; in {
  flake.nixosModules.dms = {
    imports = [ inputs.dms.nixosModules.default ];
    programs.dank-material-shell = shared;   # no systemd: HM owns the unit
  };
  flake.homeManagerModules.dms = {
    imports = [ inputs.dms.homeModules.default ];
    programs.dank-material-shell = shared // {
      systemd = { enable = true; restartIfChanged = true; };
    };
  };
}

Risks 04 each one states what to check
▸ R1 — settings.json must stay runtime-owned
Declaring programs.dank-material-shell.settings renders the live 14 KB ~/.config/dms/settings.json as a read-only store symlink: bar layout lost, in-app edits stop persisting. This is why Neovim's matugen template cannot be enabled (it defaults off and flipping it needs a settings key). nvf therefore stays on self.scheme. owner revisit only with a settings.json translation
▸ R2 — first login before matugen has run
GTK/Qt/mango fall back to their own defaults or the static sepia values; ghostty shows its built-in colours. Everything corrects itself on the shell's first theme pass. owner cosmetic, self-healing
▸ R3 — a stylix gtk.css symlink comes back
Re-enabling stylix.targets.gtk (or setting gtk.gtk4.theme back to a theme) puts a store symlink where gtk.sh needs a writable file: DMS prints "user-managed symlink; leaving it untouched", exits 1, and the shell reports "Failed to apply GTK". Symptom to look for: a toast, not a broken build. owner watch on any stylix bump
▸ R4 — live machine drift (not repo content)
~/.config/ghostty/config exists on NIXPC as a hand-written file (plus a stale config.ghostty symlink into the repo) and already sets theme = dankcolors. It is not managed by the flake; the wrapper's flags win over it, so the two now agree. Worth deleting by hand once. owner manual cleanup
