Split the Nix store
across two disks?

mergerfs can union /nix/store with a folder on the 2 TB drive, and it is the idea the Stack Overflow answer leads with. Nix does not treat the store as a pile of folders, though — it treats it as one immutable filesystem that must exist before nix-daemon starts. And NIXPC does not need the union: the store is 61 GiB while / has 138 GiB free, because 152 GiB of already-dead data is parked in ~/.local/share.

VERDICT

No to mergerfs — and you do not need any split. Empty the Trash (90 GiB, one 49 GiB archive) and move the Steam library (62 GiB) to the /mnt/2tb-ext4/SteamLibrary that already exists: / goes from 138 GiB free to roughly 290 GiB, which is 4.7× the current store. If you later genuinely outgrow NVMe, option C (local-overlay) is the only layering Nix supports; option B (move /nix wholesale) is the only one that keeps the store on a single filesystem.

What the SO answer is / and why mergerfs breaks here

That question has two answers. The accepted one is a survey of six different strategies and the union-filesystem section is a generic pitch for mergerfs — it even marks the cost itself ("at the cost of performance") and never mentions Nix's immutability, atomic-commit or boot-ordering requirements. The other answer states the constraint plainly: "as far as I know it is not possible to share nix across multiple disks transparently without either LVM/ZFS … or write your own fuse overlay for nixpkgs … you need to ensure /nix/store contains enough stuff to boot before the fuse overlay is started." That is the real blocker, and NixOS makes it worse in a way the answer only half-guesses.

01

The store is deliberately one immutable mount

◈ BLOCKING // the seam is NixOS's, not yours

On this machine /nix/store is not a plain directory — it is a read-only self-bind of /dev/nvme0n1p2[/nix/store]. NixOS applies it at boot from boot.nixStoreMountOpts:

Defines the mount options used on a bind mount for the /nix/store. This affects the whole system except the nix store daemon, which will undo the bind mount. ro enforces immutability of the Nix store.nixpkgs · nixos/modules/system/boot/stage-2.nix
# live state on NIXPC right now
$ findmnt -rno OPTIONS /nix/store
ro,nosuid,nodev,relatime,x-initrd.mount

$ systemctl show nix-daemon.service -p RequiresMountsFor
RequiresMountsFor=/nix/store /nix/var /nix/var/nix/db

So a union has to be inserted under that seam and be live before nix-daemon starts — and the daemon will then undo the top mount, which would now be yours.

02

mergerfs cannot rename or link across branches

◈ BLOCKING // EXDEV is the documented answer

Nix commits a store path by writing a temporary name and rename()-ing it into place, because a hash-addressed path must be all-or-nothing. mergerfs's own docs describe exactly that pattern as the one it cannot serve:

there is no way to link or rename from one of the underlying branches into mergerfs. They are different filesystems even if logically they seem related.

it is common and even best practice for a program to write to a temporary file first and then rename to its final destination. That temporary file name will typically be random and have no indication of the type of file being written.mergerfs · FAQ → Technical Behavior and Limitations

"Split of files across branches" is also on mergerfs's own non-features list. Nix tolerates EXDEV on some moves by falling back to a full copy — which means every store-path addition can degrade into copying a whole closure through FUSE.

03

Placement is a guess, decided per create

◈ BLOCKING // the DB and the disk can disagree

Path-preserving placement is what makes the mergerfs pitch sound like it fits Nix — but it is best-effort, evaluated when the file is created, against free space:

This is why it is impossible for mergerfs to choose the branch for a create based on file size or the source of the data. … if the source of a link or rename is on branch A but the target directory is on branch B, given the whole point of the policy is to strictly enforce behavior based on what branches already exist, it must return EXDEV.mergerfs · FAQ

Nix's temp name and its final name are unrelated strings, so nothing guarantees they resolve to the same branch — and the store's SQLite database records the path as valid either way.

04

Boot depends on a disk marked nofail

◈ BLOCKING // absent disk = silently partial store

The 2 TB drives are nofail — "this disk may legitimately be absent". /nix/store is needed during early boot, before nix-daemon, for systemd itself. mergerfs advertises this as a feature, which for Nix is the worst possible failure mode:

Unaffected by individual filesystem failure

What happens if a branch filesystem blocks? … If enough threads block then mergerfs will block. There are no timeouts or ways to truly work around this situation.mergerfs · Features / FAQ

A vanished branch does not error — the union keeps answering, with an arbitrary subset of the store missing while /nix/var/nix/db still claims every path is valid. Plus the bootstrap circle: the mergerfs binary you need to mount /nix/store lives inside /nix/store.

◈ TRADEOFF // buys one filesystem, spends NVMe speed

$ rsync -aHAX --info=progress2 /nix/ /mnt/2tb-ext4/nix/

# then, in the flake:

C

local-overlay store

◈ TRADEOFF // the supported layering, at the price of a frozen base
# Nix 2.34.8 has it; the feature flag is off today
nix.settings = {
  extra-experimental-features = [ "local-overlay-store" ];
  store = "local-overlay://?root=/nix"
        + "&lower-store=/nix/base"
        + "&upper-layer=/mnt/2tb-ext4/nix-upper";
};

# Nix VERIFIES the mount, it does not mount it. You supply,
# before nix-daemon starts (upperdir and workdir: same volume):
$ mount -t overlay overlay \
    -o lowerdir=/nix/base/nix/store \
    -o upperdir=/mnt/2tb-ext4/nix-upper \
    -o workdir=/mnt/2tb-ext4/nix-work \
    /nix/store
PRO
The only layering Nix actually supports — it validates the mount itself.
PRO
Kernel overlayfs, not FUSE: hard links, renames and xattrs behave.
CON
Lower store "must not change at all" while mounted → GC can only ever reclaim the upper layer; the base's 61 GiB becomes permanent. Verify this before adopting.
CON
No NixOS module: you hand-write the overlay mount plus daemon ordering, and it still depends on the big disk at boot.
CON
Experimental; the lower store's metadata has its own grow-only restriction.

Open questions 03
▸ Q1 — Is 290 GiB of headroom enough, or does this decision come back?
The store is 61 GiB at 70 787 paths and grows with every nixos-rebuild generation. Track it: du -sx --block-size=1G /nix/store. Under ~8 GiB/month, 290 GiB is years of room. Above it, revisit option C before reclaiming anything else — and measure first, do not assume.
▸ Q2 — Does nix store gc reclaim space from a local-overlay lower layer?
This single question decides C versus B. Nix's own docs say the lower store "must not change at all" while an overlay store is mounted on it, and that "deleting or modifying store objects is not allowed in general". If that means the base is frozen, then GC permanently stops reclaiming the 61 GiB you started with — a bad trade on a store you collect to save space. Test it on a throwaway store before committing.
▸ Q3 — deferred: is auto-optimise-store worth enabling?
Not a reason to act. auto-optimise-store = false, but nix-optimise.timer is active and ran most recently on 2026-10-11 — so the 61 GiB is already the deduplicated size. Turning the per-build flag on changes nothing about the space question.
