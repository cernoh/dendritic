ext4 vs ZFS vs XFS
for this NixOS box

You are on ext4 on a 466 GB NVMe root, with 32 GB RAM and three idle HDDs (2×1.8 TB + 931 GB). For a single-disk NixOS desktop root the boring answer wins — but those HDDs change the second half of the answer. Reader-who-stops-here version: keep ext4 on /, put ZFS on the bulk disks.

Prompt that produced thiswhats the best file system to use? Ext4, zfs or xfs — context: currently ext4 on /dev/nvme0n1p2 mounted on / (df -T + findmnt confirmed), 32GB RAM, NVMe 466GB + sda 1.8T + sdb 1.8T + sdc 931GB, dendritic NixOS (NIXPC x86_64 / ASAHI aarch64)
Selected

Option A (ext4) for / — plus Option B (ZFS) for /data. Keep the NVMe root on ext4: zero NixOS friction, shrinkable, fast enough. Build the three HDDs into a ZFS mirror pool for bulk data where checksums, compression and snapshots actually pay. XFS only if your root becomes a large-file video/VM volume.

ZFS — bulk pool, not root

◈ TRADEOFF // gives up simplicity + RAM to buy integrity at rest
# mirror the 2x1.8T, keep 931GB as spare / scratch
zpool create -o ashift=12 tank mirror sda sdb
zfs set compression=zstd tank
zfs set atime=off tank
zfs create tank/data  # mount at /data

# NixOS side (pinned kernel + hostId required)
networking.hostId = "8425e349";
boot.supportedFilesystems = [ "zfs" ];
PRO
End-to-end checksums + scrub: only option that detects HDD bitrot.
PRO

XFS — large-file specialist

◈ TRADEOFF // gives up shrink + integrity to buy parallel throughput
# format + mount for a video / VM / build volume
mkfs.xfs -L data /dev/sdc1
# /etc/fstab
LABEL=data  /data  xfs  defaults,noatime  0 2

# grow later is online; shrink never is
xfs_growfs /data
PRO
Best sustained throughput on large files + parallel I/O (video, VMs, builds).
PRO
Online grow + defrag (xfs_fsr); mature, kernel-native, low NixOS friction.
PRO
Fast mkfs/fsck on multi-TB volumes where ext4 fsck drags.
CON
Cannot shrink — layout mistakes are permanent without reformat.
CON
No checksums, no snapshots, no compression — same integrity story as ext4.
CON
Small-file + metadata-heavy trees (nix store!) measurably slower than ext4.

Open questions 02
▸ Q1 — Are the three HDDs free to pool, and is the data replaceable?
If sda/sdb/sdc hold data you need, the ZFS pool build needs a backup target first — pooling destroys contents. Owner: you. By: before any zpool create. If they are spare, the mirror can be built today and mounted at /data without touching /.
▸ Q2 — Does any volume hold hours-long video renders or large VM images?
That is the only case that flips a volume from ext4 to XFS. For the Nix store itself (metadata-heavy, many small files) ext4 stays faster — do not put /nix on XFS without measuring. Why not blocking: root decision is already made; this only shapes a future /data subvolume.
