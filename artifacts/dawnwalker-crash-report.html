Incident / Blood of the Dawnwalker / 2026-10-15

The game dies inside
the Steam overlay's
present hook

Every launch of The Blood of Dawnwalker on NIXPC today survived between 2 and 8 minutes, then the process aborted. The one core dump that exists was delivered while the vkd3d_queue thread was executing gameoverlayrenderer.so — exactly the frame identified in the 2026-10-14 session, whose recommended fix (stop the overlay from running) was never applied: EnableGameOverlay is still 1. A second, independent defect (595 driver rejecting the title's WaveSize(64) compute shaders) is also still live.

Prompt that produced thisthere have been multiple crashes when trying to play blood of the dawnwalker
PRIMARY

Option A — disable the overlay's Vulkan layer in the launch options. The 14:31:52 abort's return address resolves into VulkanSteamOverlayPresent (gameoverlayrenderer.so +0x8bf06), reached from the vkd3d-proton present path. Free, reversible, no rebuild. The driver pin (Option B) is the second lever, and per the 2026-10-14 session it is not what a Proton swap can reach. The freeze at 14:39 is the same hook one layer deeper — its connect() to the overlay's IPC socket never returns because that socket's accept queue is full, so the whole frame parks with the GPU idle. Both symptoms are one cause; Step 1 addresses both.

What it is not / nothing here is a GPU, VRAM or driver failure

While frozen: no thread burned CPU (0–2 ticks per 4 s across all 109), GPU 28 % falling to 4 %, SM clock 517–1095 MHz against ~1900 under load, VRAM held at 6.5 GiB, and zero Xid, DRM-reset, OOM or swap events in the journal. 39 threads sat in fsync_wait_objects/NtWaitForSingleObject, 7 on futexes, 2 inside the overlay's own read() at +0x52b1b. That is one stuck call site with everything behind it parked — not the 2026-10-14 shader-compiler spin (which pegged a core in libnvidia-gpucomp), and not a VRAM or driver hang.

Live recovery: kill 407762 (the wedged listener) makes the pending connects fail at once with ECONNREFUSED, which releases the present path; Steam may respawn the UI, but on an empty queue. Nothing recovers a session whose accept thread is already wedged — the fix is to stop the layer loading at all (Step 1).

Caveats 05 Stated so the next session does not over-read this
▸ Only one of the six ended launches left a core
Frames are proven for the 14:27 launch only. The other five ended without a dump, which is what a hung-but-alive process looks like when it is closed, and also what the title's own crash dialog looks like. The abort is therefore a confirmed kill for at least one launch and a candidate for the rest — not a proven count of six identical aborts.
▸ There are no game logs to read — and this repack is why
Saved/Logs/ is empty and no Saved/Crashes/ exists for this install: the Kryoto build ships a patched binary (steam_api64.dll.kryoto, Engine/…/steam_settings/) with no vendor support, so the usual Unreal log trail is absent and every conclusion here had to come from the core dump, Steam's own logs and the Proton log. Practical consequence: a retail copy on the same driver would be the cleanest way to separate "this title" from "this build".
▸ The obvious fix is documented as not working — untick nothing
Valve's steam-for-linux #13669 (overlay Vulkan layer dies in VulkanSteamOverlayPresent via vkQueuePresentKHR; fixed in client 1790904859) records that clearing Enable the Steam Overlay while in-game still leaves ENABLE_VK_LAYER_VALVE_steam_overlay_1=1 and gameoverlayrenderer.so in LD_PRELOAD, and that the layer's own DISABLE_VK_LAYER_VALVE_steam_overlay_1 is ignored too. Only VK_LOADER_LAYERS_DISABLE removes it. That is why Step 1 is the launch option and not a checkbox.
▸ Steam client build: past that specific fix, same failure shape
The installed client reports Client version: 1791918634 (2026-10-14), newer than the 1790904859 build in which #13669 was confirmed fixed. So this is not that regression re-appearing by build number — the frame merely shows the same function is again where the process dies. Keep the client updated, and if Step 1 resolves it, the frame is worth reporting upstream with this core.
▸ Prior sessions and the record they left
2026-10-14 “Debug Dawnwalker.exe crashes under Wine” isolated this same overlay abort from a systemd core and recommended turning the overlay off — never applied. 2026-10-14 “Diagnose Dawnwalker crash from Proton log” isolated a second failure (the NVIDIA shader compiler spin) plus the WaveSize rejections, and concluded the remaining lever is the driver package, not any Proton build. Both conclusions survive; only their crash/timestamp framing of the UECC-* directories needed correcting.
